# Changelog

Version numbers refer to `SOFTWARE_VERSION` in `limbtrack/engine.py`; every recording's `meta.json` stores the version, the
meta schema and a `provenance` block (code hash, git commit, library versions, protocol hash).

## Unreleased - 2026-11-04 (the number is given when it is merged)

### Quality loop (2026-11-04): what was tested, what was found, what changed
Tests chosen for this software (a Windows desktop program run by a few researchers; a wrong number ruins a study): unit, integration and end-to-end tests, static analysis (ruff with a bug-finding rule set only, bandit), complexity and dead code (measured), dependency and licence audit, load and resource profiling, accessibility, heuristic evaluation, an automated cognitive walkthrough, a keystroke-level count, and a code review. Not possible without people: usability tests, the 5-second test, SUS, SEQ and task-completion rates with real users (see the next pilot).
Rules kept so the code does not get worse to pass a test: no test removed, skipped or weakened (the few edits to existing tests are listed below); no blanket suppression; no feature removed; **no measured number changes** (the golden tracking test is untouched, the AnyBody export regenerated from the pilot data is identical, and `check_session` gives the same output on it); nothing refactored only to lower a complexity figure.
- **Readable on a light window:** the step chips and the dot buttons of the Live tab used bright text made for a dark window; on a light one it measured 1.3 to 1.9:1. A light window now gets darker text (5.5:1 or more); a dark window gets exactly the styles it always had (`panels.chip_style`, `gui.dot_chip_style`). `tests/test_theme_contrast.py` works the contrast out from the colours in the styles for four windows and fails if a style drops below 4.5:1, if the dark styles change, or if anything but the text colour changes. Edited existing tests: assertions in `tests/test_mark_again.py` and `tests/test_pinned_bar.py` now ask `dot_chip_style` for the style of the window's theme instead of reading the dark dictionary (the 'armed' ones are the same in both and unchanged).
- **Named for a screen reader:** the arrow buttons, the picture slider, the drop-downs and the angle and force tables of Review. The Review Privacy button has the key **P**. `tests/test_accessibility.py` fails when a visible control has no name, and when a control that never takes the keyboard names no key. Review still has buttons that only the mouse reaches (the Original / Reviewed and Trial / Overview switches, Reference angle, More numbers, Note): a decision, not changed here.
- **The Markers hint** now also names the manual choice ("or tick that you mark the MVIC by hand today"); with a force connected the step is not done until one of the two is chosen, and the hint named only one.
- **A whole session as a test:** `tests/test_session_walkthrough.py` drives the real window with a video as the camera and does only what the instruction line says (an automated cognitive walkthrough), counts the actions (a keystroke-level estimate and a friction budget of 25 for the first trial; 21 measured) and then checks that the saved trial passes `check_session`, opens in Review, takes a verdict, exports, and that no recorded file changed. A video file cannot be recorded with force (the program says so); the live-camera path is covered in `tests/test_force.py`.
- **Static analysis:** unused imports and variables removed; a function defined inside the torque loop moved out (same numbers); the unused `MetricCard` class and its stylesheet rules removed. Not touched on purpose: the 52 `app = QApplication...` lines the linter calls unused (the assignment keeps the Qt application alive). `tests/test_originals_untouched.py` now also covers the Privacy copies.
- **Review of this change (a code review at high effort):** found and fixed a crash of the check on an empty force file, trials with no saved video being called unprotected, a truncated protected copy counted as complete, a stale "I looked" tick silencing the privacy check, a folder called review above the chosen one hiding every trial, and repeated disk reads and rescans in the Privacy window and the check list. Each has a test that fails without its fix.
- **Dependencies:** no known vulnerability in the runtime libraries or their dependencies (pip-audit); licences are permissive except PySide6 / Qt (LGPL-3.0). `requirements-lock.txt` holds the exact versions the pilot data was recorded with.
- **Measured, not changed:** the cost per picture with seven dots is a few milliseconds with recording and the 1 kHz force running; handles and threads stay constant over repeated record / stop / open cycles; process memory on Linux grows with repeated recordings while the force runs, which is the allocator keeping freed memory (it vanishes when large blocks are forced through mmap) and not a leak in the program. Complexity: 16 functions rate F; the largest are `protocol.validate_protocol`, `gui.update_steps`, `dot_edits.apply` and `analysis.trial_check_items`; none refactored.

### Also in this change (audit of 2026-11-04)
- **An independent after-session check, `tools/check_session.py`:** `python tools/check_session.py recordings` re-derives, from the saved files only, what the numbers claim and says **FAIL** where they disagree with each other
  (time going backwards, newtons not equal to (volts minus zero) times slope, force and pictures not on one clock, an angle that is not what its dots give, missing picture rows) and **WARN** where they are consistent but may not mean what they seem
  (no zero, the input limit reached, a load beyond the heaviest calibration load, a resting force far from zero, a dot lost or moved apart or mislabelled at the force peak, the angle far from the position's target, a dot that jumped,
  an inconsistent ruler scale, an iliac crest dot that is not a stable landmark). It imports nothing from the program's analysis, so a mistake in the program cannot also be in the check, and it never writes. Run it after every session, before the data is
  used. `tests/test_check_session.py` (18) records a trial, damages copies of it in each of those ways and checks that each damage is named; breaking the check on purpose (four ways) was noticed every time. The thresholds are named constants at the top of the file.
- **A video file's folders no longer reach `meta.json` off Windows:** the source is recorded by its file name only, splitting on either kind of slash (`camera.py`); with a Windows path on another system the user's folder names were kept.
- **Anonymised in the repository** (wording only, no measured data): the researcher's Windows user name in paths (`HANDOFF.md`, `LoadCellCalibration/`, a test default), a phone model, and the body size of an AnyBody model.
- **Tests that failed only on a non-Windows computer** now test the same thing there: the worker-process helper (`pid_alive`), the width of the Fix-dots column (off Windows the font is pinned, because the pane asks for exactly what its number columns need; on Windows the real font is used, so nothing is made easier to pass there), and the read-only test (it needs a user who is not an administrator).

### Fix the privacy crop and masks in Review (the open item of `PARKED.md`, asked 2026-10-31)
- **Why:** the crop and the black masks are set in the Live tab before recording, and `privacy.apply` changes only the saved copies. When the recorder forgot (no crop, no mask, a face outside what was covered), the saved `raw.mp4` and `overlay.mp4`
  show the unprotected picture, and Review could neither say so nor put it right.
- **A check:** a trial recorded with neither crop nor mask, where the operator did not tick *I looked: nothing identifies the participant*, now has the check **No crop or mask on the video** (amber, with a **Privacy** button). So has a trial recorded before the
  program kept a privacy record (`meta.json` has no `privacy`). A trial recorded with a crop or masks, or with the operator's "nothing identifies the participant", has no check. The check is a note: it does not change the verdict, a number or a file.
- **The Privacy window** (button **Privacy** beside *Fix dots*, or the check's button): a picture of the trial (a slider picks the picture), *Crop* and *Mask* modes, and a drag draws the rectangle in full-picture pixels, snapped like the Live tab's
  (even sizes, at least 32 px, at most three masks). The tracked dots are drawn on the picture; a dot that the drawing would cover, or cut off at the crop edge, is red and named with the number of pictures, before anything is made.
  **Make protected copies** writes `<trial>_raw_protected.mp4` and `<trial>_overlay_protected.mp4` (the crop applied, the masks black) in the trial's **review folder**, with a progress window that can be cancelled (a cancelled copy leaves no half file).
  **Nothing is deleted:** there is no delete button. A copy that a new drawing replaces is moved to `superseded/` in the trial's review folder, with the time in its name; no copy is ever overwritten.
- **What is kept:** the drawing and the copies made from it are in `review/<participant>/<trial>/privacy_fix.json` (the crop, the masks, which copies exist and from which drawing, an append-only history). Drawing again replaces the copies; making them again from the same drawing keeps them.
- **What does not change:** the trial's own `raw.mp4`, `overlay.mp4`, `data.csv` and `meta.json` are never written (the review layer's guard), no tracked position and no number changes (a test compares every file's SHA-256 before and after, and the CSV rows and angles).
  **The unprotected originals stay on the disk until the people responsible for the data decide** (delete, move, encrypt): this version does not remove them, and `tools/protect_originals.py` still keeps their SHA-256.
- **Limits, said plainly:** a trial recorded with a crop holds nothing outside it, so a new crop that reaches outside the old one comes out black there (the window says so). A rectangle is fixed for the whole trial, as in Live: a face that moves out of its mask in
  the middle of the trial is not covered (look at several pictures with the slider). The copies are re-encoded (`mp4v`), as the originals were. Review itself still shows the original picture on screen. Not tried on real pilot videos, only on synthetic recordings.
- **Tests:** `tests/test_privacy_fix.py` (14: the states of a trial, copies of a plain and of a cropped trial, a mask alone, drawing again and clearing, a cancelled copy, no write beside the trial, unchanged numbers, the dots the drawing would hide,
  and the check, the button and the window driven with the mouse events of a drag). The shared test trial (`humming_trial`) says the operator looked and nothing identifies the participant, as the Live tab's tick does.

## 0.35.0 - 2026-11-04

Built from `audit/IMPROVEMENT_AND_ANYBODY_PLAN_2026-11-02.md`, the features after F1-F7. **Why this version:** before the first study participant the force has to be checked against something known (plan V4: **F8, the check weight**, and **F9, the rig check list**) and the program that records the study has to be the same program, with the same settings, every time (plan V6, the code freeze: **F13, the study settings**, and a small freeze tool). **No measured number changes in any of them:** the check weight and the rig check only READ the force samples and the engine's state, they move no zero, no calibration and no setting; the study settings only READ the program's settings and compare them with a list; none of them ever stops Record (they warn, remind and log). New things are only added: new `meta.json` keys (`check_weight`, `rig_check`, `study_settings`; `null` when there is none, and a trial of an earlier version opens and exports with blanks), three new columns (two at the end of the session summary and of the AnyBody export, one at the end of the AnyBody export only), new session log lines, one new block in `protocol.json`. None of it has been tried on the real rig or on a person; the tolerances, thresholds and frozen values named below are proposals the group has to confirm.

### F8 - The check weight: the force read against a known hanging mass
- **Why:** the plan (V4) wants the force checked against a known mass before each session, so that a drifting amplifier, a wrong slope or a loose connection is seen before the participant arrives and not in the review. The load cell's regression (2026-10-13) is good to about 1 % inside 0-250 kg; nothing in the program compared it with anything on the day.
- **How it is used:** in the Force box, type the known mass in kg (20 to 50 kg; a comma works as the decimal mark; **remembered** between launches in `settings.json`, `check_weight_kg`). Press **Zero** (Z) with nothing but the hook or strap hanging (so only the mass counts), hang the mass, press **Check weight**. The program averages the zeroed force over **3 s**, compares it with mass x 9.80665 N and shows the error in percent: **green** up to 1 %, **amber** up to 2 %, **red** above (`AMBER_ABOVE_PCT`, `RED_ABOVE_PCT` in `check_weight.py`: a PROPOSAL, the group must confirm them). The average is a whole number of 50 Hz cycles (3.000 s = 150 cycles at 1000 samples a second, the rule of `force.py`: a multiple of 20 ms), so the mains hum cancels out exactly; it is not a single sample (a test puts a 15 N hum on a 245 N load: one sample is up to 6 % off, the average 0.1 %). Sign: positive = the program reads more than the mass gives.
- **When it says no (a sentence, nothing recorded, nothing changed):** the force is not connected; the reading stopped; a recording is running; there is no load cell calibration (volts only); **the rig is not zeroed**; fewer than 90 % of the 3 s of samples are there yet; the signal is not steady (the same limits as the zero: a drift of more than 10 mV between the halves, or noise above 30 mV with the hum not counted: a swinging weight is refused, not averaged); the mass is outside 20-50 kg. The box says what is missing before you press (not connected / not zeroed yet).
- **What is kept:** `Engine.check_weight` holds the latest check of the program run. It is saved in the `meta.json` of **every following trial** as `check_weight` = `{mass_kg, expected_n, measured_n, error_pct, level, ok, time, zero_v, zero_set_at, calibration_id, calibration_method, n_per_v, seconds, samples, noise_v, hum_v, drift_v, amber_above_pct, red_above_pct, note, same_calibration, note_on_values}`; `null` when none was made in this run (the key is always there); in `engine.SNAPSHOT_KEYS`, so it is frozen while recording like the other settings. `ok` is true for green only. `same_calibration` says whether the slope and regression in use are still the ones the check was made with. The check is not kept across a restart (a restart loses the zero it was made against); the session log keeps the history.
- **The session log:** every check is a line in `session_log.csv` (event `check weight`; the log's own time column; detail `mass_kg=25; expected_n=245.166; measured_n=...; error_pct=...; level=green; ok=yes; zero_v=...; calibration_id=2026-10-13; calibration_method=...; time=...`). A refused check is a line too (`check weight refused`, with the reason). `check_weight.parse_log_detail` reads a detail back.
- **A soft reminder row (like the 0.24.0 ones, never a refusal):** while the force is connected and nothing records, an amber row under the instruction line says *Check weight: none made in the last 12 h*, *the last one is over 12 h old*, *made with another calibration than the one in use*, or *the last check was AMBER/RED (+1.4 % against 25 kg)*, with **Force box** (opens the Force section) and **Noted** (silences exactly that sentence until the reason changes). 12 h (`VALID_FOR_HOURS`) is a proposal: the same idea as the participant code's 12-hour memory. What is open when Record is pressed goes to the session log and to `meta.json` `reminders_open_at_start`, as for the other reminders.
- **Columns:** `check_weight_error_pct` and `check_weight_time` are appended at the end of `analysis.SESSION_COLUMNS` (88 now: 66 + 9 stabilisation + 11 standing + these 2) and at the end of the AnyBody export's columns (after `notes`, so the 0.34.0 columns keep their places). Blank for a trial without a check; the AnyBody `notes` column then says so. The participant overview's disk cache is now format 4 (`review_layer.OVERVIEW_CACHE_FORMAT`): a cache of 0.34.0 has rows without the two columns and is worked out again once.
- **Limits, plainly:** the program cannot weigh the mass: it is what the operator typed (a plate that is not what its label says gives a wrong error). If the operator calibrated with a known weight in this session (force.py `calibrate`), the slope came from a known mass and a check with that same mass agrees by construction: the result then carries a note that it does not check the regression. The regression's single-run scatter is 0.15 kg: 0.8 % at 20 kg and 0.3 % at 50 kg, so a 1 % amber limit at 20 kg is close to the scatter, and a heavier mass is the fairer check. It checks one point; it says nothing about forces above the mass (the belt squat's 5231 N were clipped, plan D1). A check made with the hook or a strap on the cell at zero but not at the check (or the other way) shows up as an error. Not tried on the real rig.
- **Tests:** `tests/test_check_weight.py` (26: the pure rules, the 3 s average against a single sample with a 15 N hum, the signed error and the levels, every refusal, the reminder by age/level/calibration, a real-time simulated load cell through hum and noise, real `meta.json` files with and without a check, the two columns in the summary CSV and the AnyBody CSV, an old trial without the key, the real box and window, `session_log.csv` read back, the reminder row and its buttons, `settings.json` round trip).

### F9 - The rig check: one list before the participant arrives
- **Why:** the pilot's first trial came 1.0-1.6 h after the start (camera trouble on 29 October) and equipment time was mixed with participant time (plan W1). One green list, run with the **rig empty before the participant arrives**, separates them.
- **Where:** the **Rig check** button beside the *Session check* button under the session plan (Position section). It opens a window beside the program (not modal). The equipment is read on a helper thread ("Working out..." meanwhile; the picture is never held up), then the list is shown. Nothing here blocks Record or anything else.
- **The items, each green / amber / grey ("not checked") with a one-line reason:**
  - **Camera:** a live camera opened **by name** (the name the Camera section shows; amber when it was opened by number), pictures arriving (amber after 1 s without one), and the picture rate the **live loop really runs at**, from the times of the engine's last 30 pictures (`Engine.live_fps`; amber under 25 per second, the limit of the existing camera check; grey until ten pictures are in); a video file or no camera is amber/grey.
  - **Force connected:** the source connected (amber if not; grey when *No force today* is ticked), no error, samples arriving (amber after 0.5 s without one) and at least 90 % of the nominal samples in the last second.
  - **Zero noise:** the spread of the signal over 2 s with the 50 Hz hum taken out (the same definition as the zero's own noise in `force.py`), with the hum amplitude beside it (`mains_amplitude`), in mV and in newtons. Amber above **10 mV** (`ZERO_NOISE_AMBER_V`, a PROPOSAL: a third of the 30 mV at which a zero is refused; about 5 N with the 2026-10-13 slope) or with hum of 10 mV or more (`HUM_NOTE_V`; the reason names the charger and the isolated outlet). Grey until the rig is zeroed.
  - **Check weight:** F8: green when one was made in the last 12 h with the calibration in use and was green; amber when old, amber/red or made with another calibration; grey when none this run.
  - **Beeps:** the button *Play the beeps* plays three of the **real cues** (record, ramp, end) through `cues.py`'s cue player, also when the beeps are switched off for recordings, and the operator ticks *I heard them*. Green needs: played, no error from the sound system, all three taken, and the tick. A sound error is shown, not hidden; grey where sound is switched off (no screen / `LIMBTRACK_SILENT`), because a silent run proves nothing; not playable during a recording (it would cancel the recording's cues).
  - **Ruler:** the scale is marked (amber if the scale itself reports a problem; grey if not marked).
  - **Lamp:** a manual tick (*The lamp is on and the light is even*); nothing in the program can see it.
- **Saving:** *Save this check* writes one line to `session_log.csv` (event `rig check`; detail `overall=amber | camera=green: ... | force=green: ... | ...`, `rig_check.parse_log_detail` reads it back) and keeps the block for the `meta.json` of every following trial as `rig_check` = `{time, saved_at, overall, all_green, counts, items: {camera, force, zero_noise, check_weight, beeps, ruler, lamp: {state, reason}}, thresholds, note}`; `null` when it was never run (the key is always there; in `SNAPSHOT_KEYS`). It is not kept across a restart (the camera and the force are connected again then). The window says when what is on screen differs from what was saved. There is no reminder row for the rig check (not asked for; the documented routine is to run it before the participant arrives).
- **Reads only:** it moves no zero, takes no zero, changes no setting; a test compares the calibration before and after. No measured number changes.
- **Limits, plainly:** the thresholds are proposals; "heard" is the operator's word; the lamp and the ruler's quality are the operator's eyes; the picture rate is the live loop's (a rate the recording can keep is shown by the recording's own `pipeline_timing`); the zero noise is measured at the moment of the check, with whatever hangs on the rig. Not tried on the real rig: the sound call was made for real on this computer (no error from Windows; whether it was audible is for the operator), the force reading on a simulated load cell in real time.
- **Tests:** `tests/test_rig_check.py` (21: the live picture rate; each item in each state with made-up and real engine facts; the noise and hum read back from a signal with known noise and hum; the simulated load cell in real time through its reader thread, proving nothing was moved; the three beeps through the real cue player with a recording backend, a failing one, a second press, and the **real Windows sound call**; the dialog on a real helper thread with the context read on the window's thread; the tick judging at once, Check again, Save; the session log line and `meta.json` read back, null before the save and the block after; a failing read said in the window; Record not blocked).

### F13 - The study settings: a frozen list in `protocol.json`, an amber line when the program differs, and the freeze tool
- **Why:** the program remembers its set-up per computer (`settings.json`), so a setting can differ from what the study decided without anybody seeing it (on 2026-10-14 the dot colour was left on Auto and the tracking "seemed worse"; the live behaviour changed between the pilot participants P01 and P02). Until now the operator checked a table (SOP Table C1) by eye. Plan V6 asks for a code freeze: the same program and the same settings for every participant, and a way to prove it afterwards.
- **The list:** `protocol.json` has a new top-level block `study_settings` = `{"settings": {name: value}, "proposals": [names]}` (the checker refuses unknown names with a "did you mean", wrong types, values outside a sensible range, a dot colour that is not auto/white/black, a hash that is not 64 characters; lines starting with `_` are comments; the block is optional). The names are fixed in `limbtrack/study_settings.py` (`SPECS`); the block may freeze any subset. 29 are in the file now:
  - **16 settings the operator can change** (compared live): tolerance main and other joints (5 / 5 deg), dot colour (black), smoothing of the displayed angles (on), recording first (on), also save the overlay video (on), the camera picture asked for (1280x720 at 30 fps), ruler length (100 cm), automatic MVIC markers (on), start when the force rises by (25 N), MVIC length (7 s), stop by itself after the MVIC end (2 s), sound cues (on), tick during the hold every (1 s), force smoothing on screen (100 ms), the load cell calibration in use (`2026-10-13`).
  - **13 numbers fixed in the program's code** (they can only differ if the code was changed, so a difference means the code is not the frozen code): the tracker's settings as one SHA-256 hash of every number in `tracker.py`, the window of the displayed-angle smoothing (0.2 s), the peak-force averaging against hum (20 ms), the sliding-window peak (500 ms), the force smoothing Review starts with (100 ms), the rests (60 s same position, 120 s next position, 30 s after the submaximal contraction), the 10 % rule, at most 3 trials, 2 planned, and the resting-force span (3.0 to 0.5 s before the push).
  - **Where the values come from:** the SOP's Table C1 where it states one; else what the program does on 2026-11-04. `proposals` names the 11 values the group has **not** confirmed (tolerance 5 deg, because the SOP says "10 deg after the pilot, if 5 is not possible"; the 25 N start, which the SOP marks "confirm" while the program's default is 10 N; recording first; the calibration id; the tracker hash, as D10 (the freeze) is not decided; the peak averaging, the 500 ms and 100 ms windows, the planned number of trials, the resting-force span).
  - **Not in the list, and why:** the picture delay (a Review box that starts at 0 and has no setting or constant; the tap test V5 is still open), the recordings folder (a path), the tested leg and "Participant faces" (per participant and chosen at Record; they already have their own reminders and checks).
- **The comparison:** `study_settings.py` (pure rules, no Qt) reads the engine and the program's constants and returns, for every frozen setting, `same` / `differs` / `not_checked` with a plain sentence (*Dot colour: "auto" now; the study says "black". (Dots section)*). A setting that cannot be read now (the force is not connected, no camera is running, the automatic markers are off so their threshold means nothing) is **not checked**, never a difference and never a guess; the record lists what was not checked.
- **The Live tab:** an amber row (*Study settings: 2 differ from the frozen list (Dot colour; Ruler length)*) in the soft-reminder bar, only while something differs and nothing records, with **Show the list** (all differences, then what could not be checked, with a note where the study's value is a proposal) and **Noted** (silent until the list of differences changes). It needs no camera. It never refuses Record: it is also in `reminders_open_at_start` of the trial and in the session log's "recording started with reminders open" line.
- **The session log:** one `study settings` line once at start-up and again whenever the differences change (and have stayed changed for 1 s, so a spin box held down is one line; not while recording): `checked=22; not_checked=7; differs=2; dot_kind=auto (study black); ruler_length_cm=15.0 (study 100.0)`. Without a block one line says so. `study settings reminder dismissed` for *Noted*.
- **`meta.json`:** `study_settings` = `{settings_frozen: [names], differences: [{key, label, expected, actual, text}], not_checked: [{key, reason}], proposals, block_sha256, note}`; `differences` is an empty list when nothing differed, the whole value is `null` when `protocol.json` has no block (and the key is absent from trials of earlier versions). It is the state **when the recording started**; it is deliberately not one of the `SNAPSHOT_KEYS`, because the force smoothing and the ruler length are display settings that can be touched while recording and would otherwise print a false `changed_during_recording`. The protocol hash saved in every trial (`provenance`) changes because the file has a new block.
- **Review:** an informational line (level `info`, area recording, headline "Settings differ from the study (2)") for a trial recorded with differences: "The numbers are what was measured; this only says the set-up was not the study's." It is not a `check`, so `checks_to_look_at`, the overview's "needs a look" and the verdicts are unchanged.
- **The AnyBody export:** one appended column `study_settings_differences` (a count; blank without a block, with a line in `notes`); not in the session summary (`SESSION_COLUMNS` and the overview cache are unchanged).
- **The freeze tool:** `tools/freeze_check.py` prints what to paste into the study log before a participant: the git commit and branch, whether the working tree is clean (changed or new files are named; a commit only reproduces the program when there are none), the tags at the commit, the program version, the hash of `limbtrack/*.py` and the protocol hash (the two every trial carries), the frozen settings (`*` = a proposal) and whether the 13 fixed numbers are still the frozen ones. It only reads: it never tags, commits or writes (a test compares `git status`, the protocol file's time stamp and HEAD before and after). `--strict` makes the exit status 1 when the tree is not clean or a fixed number differs. Today it says "NOT CLEAN" because 0.34.0 and 0.35.0 are not committed.
- **After a deliberate change of the tracker** (the golden test is regenerated): run the tool and paste the new `tracker_settings_sha256` into the block; until then the Live tab and every trial say the tracker differs.
- **Not tried:** on the real rig or a person; the tool was run on this working tree, not on a clean tag (there is none: D10, the freeze version, is the group's decision). The amber row was looked at in an offscreen window only (no fonts).

### F5 - Stabilisation measure: did the pelvis and the neighbouring segment stay still from rest to the peak force?
- **Why:** the AnyBody model assumes the pelvis and the thigh are held (README of the seated knee model: hip held 2036 N, hip free 555 N, a factor 3.7), and SOP 10.3 only says the test leader "watches for compensation (trunk lean, pelvic tilt, lifting off the support)". Nothing in the program said how much anything moved.
- **What:** `limbtrack/stabilisation.py` (pure logic), from the dot tracks a trial already has. For each dot of the pelvis: the **rest level** is the median of its positions over the same stretch the resting force uses (`Trial.force_rest`: 3.0 to 0.5 s before the push began), the **peak position** is the mean over the pictures within 0.1 s of the peak force plus the picture delay (the same pictures that give the angle at the peak force, `Trial.angle_near`); lost pictures are left out and nothing is filled in. It gives **(1)** the shift of the iliac crest dot and of the trochanter dot (frontal tests: the two ASIS dots) in cm at the ruler scale, or in pixels without a ruler (then not judged), **(2)** the rotation in degrees of the pelvis line (crest to trochanter; frontal: ASIS to ASIS) and **(3)** the rotation of the neighbouring segment that must stay still. Rotation is "clockwise in the picture" for a participant facing right; the picture is mirrored for one facing left so the same movement has the same sign; a flag uses the size only.
- **Which segment must stay still (decided per test, written in the module text):** knee extension and knee flexion: the thigh (trochanter to lateral epicondyle) as well as the pelvis. Hip extension (knee straight and 90) and hip flexion: the pelvis only (the thigh is the segment tested; the pelvis line is the answer; there is no second segment). Ankle plantarflexion and dorsiflexion: the shank (fibular head to lateral malleolus) and the pelvis. Hip abduction and adduction (frontal): the pelvis line between the two ASIS. Belt squat: computed and exported but **not judged** (a closed chain, the pelvis and thigh move by design). A test the module does not know gets the rule of its main joint. A test pins that every test of `protocol.json` has a rule.
- **Limits (a PROPOSAL for the group to confirm; the SOP gives none):** `PROPOSED_DISPLACEMENT_LIMIT_CM = 1.0` for a pelvis dot and `PROPOSED_ROTATION_LIMIT_DEG = 3.0` for the pelvis line and the still segment, two named constants in `stabilisation.py`. Chosen so that a flag comes before the angle leaves its 5 degree tolerance (a pelvis that turned 3 degrees already moves the hip angle by about 3). A flag never changes a number. On the pilot (P01, P02: 128 trials; 103 had a clear rest and could be measured, the 25 others have blanks) the pelvis dots moved a median 3.3 cm and the pelvis line turned a median 4.3 degrees between rest and the peak force (largest dot shift: 10th to 90th percentile 1.0 to 5.3 cm; pelvis rotation 0.4 to 8.6 degrees), so **with the proposed limits 87 of the 100 judged pilot trials are flagged**. The limits do not separate good trials from bad ones on this data: the group has to choose them from this distribution (or decide that the numbers are for the model and not for a flag).
- **Where it shows:** a line in Review's checks list (area *position*): amber *Pelvis or segment moved under load* with the numbers and "the group has not confirmed one" when above a limit, green *Stabilisation within limits* when not, a green note *Stabilisation: not judged* in the belt squat. No line when it cannot be measured (no force, no clear rest before the push, no pelvis dots). The sentence is also in the export column `checks_to_look_at` when it is amber (the only existing column whose text can change: it lists the checks, and this is one more check).
- **Export (new columns, appended at the end of `analysis.SESSION_COLUMNS` after the 66 that were there):** `stab_unit` (cm or px), `stab_dot1_name`, `stab_dot1_shift`, `stab_dot2_name`, `stab_dot2_shift`, `stab_pelvis_rot_deg` (signed), `stab_still_segment` (thigh, shank or blank), `stab_still_rot_deg` (signed), `stab_flags` (the sentences, joined by "; "). **Blank** where the trial has no force, no clear rest, the dots are lost, or the trial was recorded without the dots; never a made-up number.
- **Cache:** the participant overview's cache on disk is now format 3 (`review_layer.OVERVIEW_CACHE_FORMAT`): a cache of 0.33.0 has rows without the new columns and is worked out again once.
- **No existing measured number changes:** the rows of a trial are the same in all 66 old columns (a test switches the new measure off and compares), except the text of `checks_to_look_at` gaining the stabilisation line when amber. Review never writes the recorded files.
- **Limits, plainly:** a 2D picture: a pelvis that rotates about the vertical axis or a trunk that leans towards the camera is not seen. The cm are right only at the ruler's distance in the picture's plane. The crest dot is on skin over the pelvis, not on the bone. The camera or the ruler moving is not noticed (the ruler dots are fixed points, not tracked). The limits are a proposal; no pilot data was used to choose them. Not tried on a person or the real rig.
- **Tests:** `tests/test_stabilisation.py` (22: made-up tracks with hand-worked numbers, the sign for both facings, the 180 degree wrap, the picture delay, lost dots, no ruler, the rule of every test, and three real recordings with a moving or still pelvis, read back through Review's checks, the export row, a CSV file, a copy of a trial with the crest dot lost, a trial without force).

### F4 - A standing reference: hip, knee and ankle offsets at the anatomical zero, and the segment lengths in the picture
- **Why:** the crest dot is not on the pelvis' midline, so the hip angle read from the dots differs from the joint's by 10 to 25 degrees standing and 36 to 71 degrees "sitting at 90" (pilot review F7b), and the model needs a zero posture. 0.33.0 built the angle reference (a joint called 0 while the dots read 10) by hand, one angle at a time.
- **What (a thin layer on the angle reference of 0.33.0, not a second mechanism):** a box **Standing reference** in the Position section (`limbtrack/standing_reference.py` pure rules, `standing_reference_box.py`, `Engine.start_standing_reference` and friends). With the participant standing in the anatomical position and all dots marked (the foot dots too, for the ankle), press **Capture 3 s**; the program reads the unsmoothed hip, knee and ankle angles (the same 0.2 s average the angle reference uses) in every picture for 3 seconds, and at the end sets, **through the same angle reference**, the offset of every angle that was steady: the joint is called 0 degrees (the anatomical zero of all three angles in `protocol.json`), or the number typed in the optional goniometer / inclinometer boxes, and the offset is the mean of the dots minus that. The picture, the target and the verdict then use them exactly as for a hand-set reference (the angle from the reference first, the dots' own beside it, 0.33.0). It also keeps the **segment lengths** in the picture (thigh, shank, foot, pelvis line; cm at the ruler scale, else pixels).
- **Safeguards:** an angle that moved during the capture (standard deviation of the dots' angle above `MAX_SD_DEG` = 2 degrees, a proposal) or was readable in fewer than 80 % of the pictures (or fewer than 10) is **not set**, and the message says which and why; the others are. No participant code, a break, a recording, a number that is not an angle, or no readable angle refuses the start with a sentence. The capture is cancelled by a change of test or dots, by no picture for half a second, and by pressing Record. Pressing the button during the capture cancels it.
- **How it combines with an angle reference set by hand (decided and tested): the latest wins, per angle.** Pressing the standing reference replaces a hand-set reference of any angle it captured (the message says which); setting one by hand afterwards replaces the standing one of that angle; an angle the capture could not read keeps what it had. `meta.json` says which angles of the trial still used the standing offset (`in_use_in_this_trial`).
- **Kept for the participant:** the record belongs to the participant code (it is not the live reference: the live angle reference goes, as before, when a dot is marked again or removed or the dots are reset), comes back in a restart within 12 hours (`settings.json` session part `standing_references`) and is saved in **every later trial** of that participant, so the offsets and the lengths are in the export even for a trial recorded after the dots were marked again, when no live reference was in force. Review says so in an info line (*Standing reference in the file*: used in this trial, set by hand instead, or not used because the dots were marked again).
- **Saved:** `meta.json` `standing_reference` = `{taken_at, test_key, facing, capture_s, pictures, instrument, angles: {hip|knee|ankle: {reading_deg, reading_source, dots_deg, offset_deg, sd_deg, pictures}}, skipped, segments: {unit, px_per_cm, lengths: {thigh, shank, foot, pelvis}, dots}, note, in_use_in_this_trial}`; `null` without one; in `engine.SNAPSHOT_KEYS`. A trial of an earlier version has no key and opens and exports with blanks.
- **Export (new columns, appended after the stabilisation columns; only what 0.33.0 did not have):** `standing_taken_at`, `standing_hip_offset_deg`, `standing_knee_offset_deg`, `standing_ankle_offset_deg`, `standing_basis` (what each angle was called), `standing_in_use` (which angles of this trial used it), `standing_length_unit`, `standing_thigh_len`, `standing_shank_len`, `standing_foot_len`, `standing_pelvis_len`. The 0.33.0 columns (`angle_reference_offset_deg`, `angle_at_peak_force_from_reference_deg` and the others) are as before.
- **No measured number changes:** `data.csv` is the dots' angle, always (a test compares a trial with and without the capture); the standing offsets act only where an angle reference is set, which is the 0.33.0 behaviour.
- **Limits, plainly:** an offset removes a constant difference. A standing person need not have the same offset as a seated one (the pelvis tilts, the lower back flexes, the thigh soft tissue moves), and the dots are marked again when the participant sits down, so the live reference does not carry over into the seated tests; the offsets are saved to be looked at beside the seated instrument readings (reference readings, 0.16.0), not to correct them silently. Review does not apply the standing offsets to a trial that was recorded without them (it could, through the reference dialog; not built). Only a side-view test: no frontal tests. The foot dots are the weak point (0.24.0). Not tried on a person or the real rig.

### F1 - The AnyBody export: one row per participant and position, and a participant.json
- **Why:** the strength factor `s = F_measured / F_model_max` is worked out in AnyBody, one model input per participant and position. Until now the numbers had to be picked out of the session summary by hand (66 columns, one row per trial, no participant measures, no strap place, no choice between two trials) and typed again. The plan's data contract M1 (section 4) says what one row must hold.
- **What:** *Export > AnyBody inputs: this participant (CSV + JSON)* in Review's participant overview writes, into the participant's review folder (`review/<participant>/exports/`, through the review layer, never beside the recordings): **`anybody_inputs.csv`**, one row per position, and **`participant.json`** (the participant's tested leg, measures in SI units, the latest standing reference, for each position the trial chosen and why a position has no row, the SHA-256 of the files of each chosen trial, and the rules used in words). Code: `limbtrack/anybody.py` (pure logic, `analysis.anybody_rows` is the name the plan gave it), `tools/anybody_export.py` (the same for every participant folder under a root, into a folder of your own, for a batch run: `python tools/anybody_export.py --root Pilot --out SOME_FOLDER [--source reviewed] [--include-unjudged]`).
- **Which trial (D3, the plan's proposal):** per position the *counted* trial with the highest peak; the other counted trial is the check (`check_trial_id`, `check_peak_diff_pct` = the SOP 10.6 number, the two smoothed peaks' difference as a share of their mean). Counted = marked **valid** (the default; `judged_only`), a real force rise (the 10 % check's own rule, 0.26.0) and not marked compromised. The highest means the highest sliding-window peak (the force that goes into the file), a tie goes to the later trial, newtons before volts. A position whose trials are only not judged yet gets **no row** and is named with the reason ("3 trials with a force rise, none marked valid yet: judge them in Review, then export again"); so are a position never recorded, one with only compromised trials, and one with no force rise. `ten_percent_check` says what the 10 % rule says of the position (ok, third trial needed, one counted trial, ...).
- **Force (D4, proposal):** `force_n` = the total force from the load cell zero (not above rest) as the highest mean over the sliding window of 0.29.0 (`force_window_ms`, 500 by default, the Review setting), in newtons; `force_rest_n` = the resting force before the push beside it, so the model's gravity rule (subtract the rest OR model the segment's weight, never both) can be applied either way; `force_peak_20ms_n` = the 20 ms peak, for comparison. A trial in volts (no calibration) gets no force, and the notes say so.
- **Angles (D2, proposal):** `hip_deg_at_peak`, `knee_deg_at_peak`, `ankle_deg_at_peak` at the peak force: the mean of the pictures within 0.1 s of the highest smoothed force, the same pictures as the existing column `angle_at_peak_force_deg` (the picture delay is taken as 0; the moment is in `angle_peak_time_s`). They are as the dots read them, in the app's sign convention (the column `angle_convention` spells it out: hip + flexion, knee + flexion, ankle + dorsiflexion), **not** AnyBody joint coordinates; a trial recorded with an angle reference also has the angle from the reference in `..._from_reference`. ## 0.22.0 - 2026-10-28

### A second zero level: the participant relaxed in the strap
- **Why:** asked on 2026-10-28 for "an extra level of zeroing the force measuring for accounting for relaxing tension". The first zero is the
  strap with nothing on it. With the participant in the position and relaxed the strap is already under some tension (the weight of the
  leg, the tone of the muscles), so "0 N" and "relaxed" are not the same level. Until now that tension was only found afterwards from the
  recording (the median 3.0-0.5 s before the push, 0.20.0), which fails when the strap was loaded before the push (P11 12:41) and which the
  operator could not see during the session.
- **What:** new button *Zero 2: relaxed in the strap (X)* under *Zero (Z)* in the Force box. It takes 2 s of signal (`RELAXED_SECONDS`;
  the same noise limit as the zero, the same 10 mV drift limit, so it is refused while the strap or the leg is still settling) and keeps it
  beside the zero (`ForceCalibration.relaxed_v`, `relaxed_n`, `relaxed_se_v`, `relaxed_when`, `relaxed_for`). It needs the zero first. It
  belongs to one participant, test and target (`Engine.relaxed_key`): in another position it is not used and the Force box says so. A new
  Zero clears it (the set-up changed). Not remembered between sessions, like the zero.
- **Live:** the Force read-out gets a second line *above relaxed X N*, and the picture header (also in the saved overlay video) reads
  *Force 312 N (+0.593 V) above relaxed 140 N* when a relaxed level is valid for the position.
- **Saved:** every `meta.json` has `force.relaxed` (volts, newtons above the zero, noise, taken, taken_for, `this_trial`, meaning) and the
  relaxed fields inside `force_setup.calibration`. **The newtons of the trial, `force_peak`, the volts and everything else are unchanged:
  the newtons stay the total force from the first zero** (the AnyBody rule of 2026-10-26: one of rest or modelled gravity, never both).
- **Review and exports:** the force text gets *relaxed (Zero 2)* and *peak above relaxed* beside *rest before*, and says whether the rest in
  the recording was higher or lower than the relaxed level taken before (the tension that eased or built up). New columns at the end of the
  per-trial `_summary.csv`: `force_relaxed_level`, `force_peak_above_relaxed`; in the session sheet: `force_relaxed`, `force_peak_above_relaxed`
  (blank when none was taken for the trial). Newtons are worked out from the saved volts with the zero now in force, so a zero recalculated in
  Review carries the relaxed level along. Trials from before 0.22.0 are read as before.
- **Not changed:** the automatic rest (`force_rest`, `force_peak_above_rest`), the 10 % check (total peak), the auto MVIC threshold, the
  SOP/protocol text (when to press Zero 2 is a group decision: the proposal is after the participant is in position and before Record).
- **Tests:** `tests/test_force_relaxed.py` (14 tests: the reading, refused without a zero or while drifting, cleared by a new zero, a real
  recording through the engine, another position not used, Review and the sheet, and the real window with the X key). The full suite
  found one thing: the first label of the button (45 characters) was longer than the panel allows (`test_no_label_in_the_panel_is_too_long_for_it`,
  42), so it was shortened.

### Hip abduction and adduction with the camera in front, and a hip centre that is computed live
- **Why:** the protocol has four frontal positions (hip abduction and adduction at 0 and 20 deg, Tabel 2), so the plan showed 15 positions instead of 19. - **Two new tests, `hip_abduction` and `hip_adduction`** (`"view": "frontal"`, positions 0 and 20 deg): the plan now has 19 positions + belt squat. - **The hip centre is a computed point** (new `derived_points` in `protocol.json`, kind `hip_centre_frontal`; an arm of an angle may end at one). Computed in every picture (a few multiplications, far below the 10 ms the tracking takes), drawn as a cyan diamond, saved as `hip_centre_x`, `hip_centre_y` in `data.csv`, defined in `meta.json` `derived_points`. **The ruler is needed** (the equation is in mm): without it the hip-centre angle is blank, the header says so, and Lock is refused (it refuses while any angle is unavailable).
- **What is and is not known about the equation:** the constants were typed from a secondary source (a biomechanics wiki, through a search summary) and the coordinate origin from a validation paper that uses the same system (PMC5121588); **the original table was not read: check it before the numbers are reported.** Independent consistency check: a cadaver study (Seidel et al. 1995) puts the hip centre 14 % of the pelvic width medial to each ASIS, 90 mm at PW 250 mm; the equation gives 89.8 mm (tested in `test_hip_centre.py`). Reported mean errors of the equation in the validation paper: about 5.9 mm sideways and 5.5 mm down; soft tissue over the ASIS adds to that.
- **The two angles do not share a zero.** Synthetic pelvis 250 mm wide, thigh 400 mm from the hip centre: the goniometer reads -4.1, 0.0, 4.1 and 12.4 deg where the thigh is 0, 5, 10 and 20 deg out about the hip centre; so the goniometer's 0 is about 5 deg and its 20 about 29 deg about the hip centre. ## 0.10.0 - 2026-10-15

### Pause for a break (with a ghost), sound cues for the MVIC, and a zero that hum no longer blocks
- **Pause for a break (P / the Pause button, live camera only).** For a rest between trials. While paused, tracking stops, nothing is judged or recorded, and the picture shows a pale **dashed ghost** of the dots, the limb lines and the dot names as they were when the break began. When the participant is back, put the stickers on the dashed circles and press **Resume**. On Resume every dot is frozen where it was and is taken back **only** when a round, right-sized, contrasty dot shows up inside its small fixed circle (the existing lost-dot rule, `DotTracker.hold`); a participant who returns in another place is not tracked, nothing is guessed, and the ghost stays until every dot is back. The locked position and its references survive the break; pausing is refused while recording; recording, locking and marking are refused while paused; *Re-mark all dots* ends a break; the ghost is cleared when a recording starts so it never reaches `overlay.mp4`. For video files the button is unchanged (play / pause and frame stepping). **No measured number changes**: on a return to the same place the angles equal those before the break within 0.1 deg (tested).
- **Sound cues for an MVIC (`limbtrack/cues.py`; Record box: *Sound cues (beeps)*, *Tick during the hold every*, *Test the beeps*).** Record pressed: one beep. **Ramp registered** (the MVIC start marker is written, by the automatic detection from the force or by the S key): two rising beeps. One second later, when the ramp should be over (**constant / hold**): one longer beep, then a short **motivating tick every second** (0 = none) during the hold. One second before the end: two falling beeps (**relax**). The MVIC end marker: one low beep. The 1-5-1 tempo follows *MVIC length* (7 s by default); the times after the ramp are counted from the detector's estimate of when the force began to rise (about 0.15 s before the marker), or from the S key. The beeps are generated in memory and played with Windows' `winsound` on their own timer thread, so a slow camera cannot make a beep late. **The first build of this made no sound at all**: Python's `winsound` refuses an in-memory sound played asynchronously (`RuntimeError: Cannot play asynchronously from memory`) and the player swallowed the error so that a sound problem could never disturb a recording; every automatic test runs silent, so none reached the real call. Fixed the same day: each cue is now played to its end on the cue thread, a failure is kept (`CuePlayer.last_error`), the window says *The beeps could not be played (...)* after *Test the beeps* and after a recording, and `meta.json` gets `audio_cue_problem` if a beep failed during a trial. Measured on this computer: every call to Windows' sound system returns about 0.1 s after the beep itself ends, the very first call about 0.3 s later still, so a silent buffer wakes the sound device when a camera starts, and cues are kept 0.15 s apart. Silent in the automatic tests and with `LIMBTRACK_SILENT` set. **The constant is announced by the clock, not detected from the force** (the hold begins 1 s after the ramp registered), and the tick is not tied to the force level: they are cues, not measurements. Switching the beeps off or changing the interval is refused during a recording; the setting is saved in `meta.json` (`audio_cues`) because **a participant who hears beeps may push differently** (this can change the force numbers; it cannot change how they are measured).
- **Zero (and known-mass reading): hum no longer blocks it, drift does.** A zero was refused when the spread of the signal over its 1 s window exceeded 20 mV, hum included. The 50 Hz hum (34 mV on 14 Oct 13:36, a raw spread of 26 mV; about 90 mV on 9 Oct) cancels out of a whole-cycle average exactly, so it never made the zero less accurate; random noise averages out too (30 mV over 1000 samples is good to 1 mV, about 0.5 N). Now: the **drift** (first half against second half of the reading) must be within **10 mV**, and the **noise** (spread with the hum taken out) within **30 mV** (it was 20 mV including the hum). Drift is what would bias a zero (a person leaning on the rig) and is checked on its own. The message after *Zero* says how noisy the zero was and how well it is known (for example *Noise 9 mV, so the zero is good to about 0.3 mV (+-0.15 N)*) and, if the hum is 10 mV or more, that the charger / isolated outlet routine matters. The zero's noise, hum and uncertainty are saved in the trial (`force_setup.calibration.zero_noise_v`, `zero_hum_v`, `zero_se_v`); older files without them still load. Applies to the known-mass calibration too. **A zero with up to 30 mV of noise is accepted, so look at the stated uncertainty before trusting a noisy one.**
- **`PELVIS_LANDMARK.md`:** the written argument (for the supervisor and the AnyBody side) for the iliac crest dot as the pelvis landmark of the hip angle, with its limits and the three checks that would turn it into evidence. Sources were looked up in PubMed; **Tabel 3 of the protocol also lists pelvic tilt (ASIS-PSIS against the horizontal), which the program no longer measures: a decision is needed.**
- `tracker.py` gains `hold()` and `hold_all()`; nothing about how a dot is followed changes (the pinned synthetic output is unchanged).
- **Not tested:** whether the beeps are audible and on time from the participant's side (only that Windows plays them without an error, and the call timing above; **nobody has heard them except you**: press *Test the beeps*); the ghost on a real camera picture; the zero on the real load cell with a hanging rig; whether the cues change what participants do.

## 0.8.0 - 2026-10-13

### Automatic MVIC start and end markers from the force
- **New tick box in the Record box: *Mark the MVIC automatically from the force*** (needs the force connected), with *Start when force rises by* (default 10 N) and *MVIC length* (default 7 s, the protocol's 1-5-1 tempo: ramp 1 s, hold 5 s, relax 1 s). **Pressing Record arms it.** When the force clearly leaves its rest level (the ramp begins) the program writes the **MVIC start** marker, and the **MVIC end** marker 7 s after it. They are the same markers the S / E keys write (same labels, CSV `event` column, `meta.json` events), so Review's window, the Check tab and the exports read them unchanged. Pressing S or E by hand takes the markers over. The picture header (and so the saved overlay video) and the Record box say *armed, waiting for the ramp* / *3.2 / 7 s* / *start and end marked*; the marker banner says *(automatic)*.
- **How the ramp is found** (`limbtrack/automvic.py`): the force (newtons without the zero, only the rise matters; volts with a 0.02 V threshold if there is no load cell slope) is averaged over 20 ms (one 50 Hz cycle: the hum cancels exactly). The rest level is the median of that signal from 3.0 s to 0.5 s before now, so a slow drift is followed and the ramp itself is never part of the reference; the force from just before Record is used, so a ramp that begins at once is found. The start is called when the force is at least the threshold away from the rest level, has moved at least 40 % of the threshold within the last 0.25 s (a slow pre-tension is not a ramp) and both hold for 70 ms (a knock is not a ramp). The threshold is raised to 6 x the noise of the rest level if the rest was unsteady. Either direction of force counts. The end marker is placed on the first picture 7.0 s after the start marker.
- **Measured on made-up force traces** (`tests/test_automvic.py`): for the protocol's ramp (400 N in 1 s) the start marker goes in **0.11 s after the force begins to rise** (100 N in 1 s: 0.18 s; 200 N in 3 s: 0.25 s; 1000 N in 0.5 s: 0.11 s), and the program's estimate of when the force really began is within 0.03 s. Ignored: 50 Hz hum of 47 N (90 mV), a pre-tension of 8 N per second, knocks of up to 50 ms, a rest that sways 6 N. A push of 15 N on a swaying rest is not called, a 60 ms knock is. In real-time recordings with the simulated force (3 runs, pictures rendered at about 20 per second) the start marker went onto the picture **0.14 to 0.21 s after the real start of the ramp** (read from the saved `force.csv`) and the end marker 2.53 to 2.62 s after the start for a set 2.5 s (the end goes on the first picture after it is due, so with 30 pictures per second it is at most 0.03 s late); the estimate of the ramp's start was within 0.001 s there (`tests/test_automvic_engine.py`).
- `meta.json` gets `auto_mvic_setup` (on or off, threshold, length; frozen while recording like every setting) and, when on, `auto_mvic`: what happened (state, the times of the markers, the force's estimated onset and how long after it the start marker came, the rest level and noise, the threshold used). Review's Check tab says the markers were automatic, or, if the force never rose by the threshold, that no start was marked (use *Window = force above half of peak*).
- **What can change a measured number: nothing.** Force volts and newtons, dot positions, angles and the CSV values are exactly as before; only the `event` column and the marker list can contain markers the operator did not press. The start marker is about 0.15 to 0.2 s later than the true start of the ramp (it is not moved back: the rows are already written); the true start estimate is saved. Markers sit on the picture time stamps like those pressed by hand, so the *picture delay* applies to them as to everything else. **Not tried:** the real load cell and DAQ (only the simulated source); check the first real session's marker against the force in Review.
- One MVIC per recording: after the end marker nothing more is marked automatically.
- **Test fix (no program change): three tests in `tests/test_analysis.py` (the two torque tests and the picture-delay test) failed on an idle computer, and on the committed 0.7.2 code too.** Their helper `humming_trial` replaces the force of a real 3 s recording with a known 17 s signal but kept the real picture times, which end at about 7.5 s on an idle machine (the recording is 90 pictures with a 33 ms wait each plus the time to render them); the tests look at 8 to 13 s. They had passed only while the computer was busy with other work (slower pictures, a longer recording), which is why the full runs of 0.7.1 and 0.7.2 were green. The helper now gives the pictures a time axis that spans the injected signal (`tests/test_force.py`), so the result no longer depends on the computer's speed.
