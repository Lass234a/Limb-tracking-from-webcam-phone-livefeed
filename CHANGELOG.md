# Changelog

Version numbers refer to `SOFTWARE_VERSION` in `limbtrack/engine.py`; every recording's `meta.json` stores the version, the
meta schema and a `provenance` block (code hash, git commit, library versions, protocol hash).

## 0.17.1 - 2026-10-21

### Reference readings: four ways a reading could be saved wrongly or not at all (code review of 0.14.0-0.17.0)
- **A new target showed the old readings in the boxes, and the next edit saved them for the new target.** Only a change of test rebuilt the boxes. Now the boxes always show what belongs to the position the window is at (test, target and participant): `LiveTab._fill_reference_boxes`, called at once when the target or the participant changes and checked again by the 200 ms refresh. `_reference_edited` sends nothing when nothing changed, and never sends boxes that were filled for another position. The old test refreshed the boxes by hand, which the program never did; it no longer does.
- **A reading typed just before F5 was not saved with the trial.** F5 starts a recording while the box still has the focus, before the box has handed its text over. Record now hands every box to the engine first (`_commit_reference_boxes`); a box that cannot be read stops the recording with a message (it would not have been saved). The box letting go of the focus when it is switched off for the recording no longer gives a "refused" message.
- **Readings were tied to the test and target only, so the next participant at the same position got them.** They now also belong to a participant: `engine.participant_code` (the code in the window) is part of `reference_position()`, and while recording the trial's own participant decides. Readings typed before any code was given belong to whoever is recorded first, and from that trial on to that participant only. The Live section says in amber when the readings belong to another participant; `meta.json` `entered_for` and `not_used.this_trial` now have `participant`. Putting a typing slip in the code right shows the readings again (they are only dropped when something new is typed).
- **Saving in Review moved every reading into the side file.** That relabelled untouched readings as *added later in Review* and split the one pair that two trials of a position share into two (counted twice in the agreement). `reference.write_sidecar(..., recorded=...)` now writes only what differs from what was saved with the trial (other numbers, or another instrument or resolution, which changes every reading) and the removals.
- **Changes no measured number.** Only which typed readings are saved with which trial.
- Tests: `test_reference.py` +4, `test_reference_live.py` +5, `test_reference_review.py` +3, and the position checks of the existing tests now include the participant. The new tests were run against the code of 0.17.0 and fail there. Version 0.17.1. Full suite: see HANDOFF.md.

### Smaller fixes from the same review
- **Frontal test without the ruler: Lock was impossible and every picture was 'not ok'.** The hip-centre angle (`"judged": false`) is blank without the ruler scale; it counted as a lost angle, so Lock always failed with the misleading "Every dot must be marked and visible", and `all_ok` in data.csv was 0 in every row. An angle that is only shown now never stops Lock, is not stored as a locked reference, and never makes `all_ok` 0 (`AngleResult.judged`, set by `angles.measure`; the main joint is always judged).
- **The tape measure of the pelvis and the wall tick carried over to the next participant** (a wrong CHECK SCALE warning, and the previous person's numbers in the next person's meta.json). They now belong to the participant code they were entered for and are cleared, with a message, when the code changes to someone else (not during a recording; checked again when it stops). Entered before any code: they go with whoever is recorded first.
- **A reading typed once and carried to the second trial counted as two pairs when no moment was stamped** (the pair was told by the stamp only). The readings now carry `typed_at` (when the typed numbers last changed, `meta.json` `reference_readings.typed_at`), and two trials with the same stamp and the same typing are one pair. Typing new numbers makes a new pair; sending the same numbers again does not. Trials recorded before 0.17.1 are counted as before.
- **'Reading taken now' could keep angles from before the camera stopped.** It is refused when the latest picture is more than 1 s old (`STAMP_MAX_PICTURE_AGE_S`), and the angles it keeps are forgotten when the dots are marked again, the test changes or a landmark is switched (`_ref_last` is cleared with the other per-angle filters).
- **Saving in Review could fail without a word** (no message under pythonw): *Save the table as CSV* while `reference_validation.csv` is open in Excel, or the readings dialog in a locked folder. Both now say what happened and what to do; the dialog stays open with what was typed, and no half-written file is left. A box that cannot be read is now named in the message (it gave the window title).
- **The frontal label checks used fixed dot names** (`asis`, `asis_opposite`, `patella`). They now take the dots from the protocol (the hip centre's definition, else the main angle's arms), so a renamed dot still has the swapped-ASIS guard.
- **protocol.json mistakes that were accepted silently** are now refused on loading: a signed angle in a frontal test (its sign would follow the hidden *Participant faces*), `"judged": false` on the main joint, and `"judged": false` on an angle with a required neighbour value (it would never be checked).
- **Force against angle: the large 'analysis window' dots were picked by the picture's time stamp,** while the window (and the Force tab) is in force time; with a picture delay they were shifted. They are now the pictures whose paired force lies in the window (`force_angle_path` gives `force_t`).
- **Less work on screen:** dragging the analysis window redraws only the large dots and the star of the force-against-angle view (not the whole path with a brush per picture); the reference rows of a trial are worked out once per load or edit; the Live reference section touches its widgets only when something changed (it runs every 200 ms).
- **Also found on the way:** a trial opened in Review after the force smoothing had been changed drew its force strip with the default smoothing while the numbers used the box (the smoothing was set after the strip was drawn). Now set first.
- **Also found on the way: two trials of the same position started within the same second wrote over each other's files** (the file name has the time to the second; a new test hit it by chance). A later one now gets `-2`, `-3` after the time (`recorder.TrialRecorder`). In normal use a trial lasts longer than a second, so only a Record pressed again at once could lose the short trial before it.
- **Changes no measured number,** except `all_ok` of frontal trials without the ruler (now 1 where the judged angles are within tolerance) and the large dots of the force-against-angle view.
- Tests: `test_frontal_engine.py` +3, `test_reference.py` +3, `test_reference_review.py` +3, `test_reference_live.py` +1, `test_force_angle.py` +3, `test_protocol_validation.py` +3 cases, `test_recording_integrity.py` +1. Full suite: see HANDOFF.md.

## 0.17.0 - 2026-10-20

### Review: force against angle
- **Why:** the first force trials showed the knee falling about 5.8 deg between rest and hold (slack in the strap, stretch, or the position slipping), which a plot against time shows only indirectly. The new view draws the joint's angle on one axis and the force on the other, picture by picture, so the shift under load is one look.
- **What:** a switch above the graphs, *Graphs: Graphs against time / Force against angle* (enabled for a trial with force; the time graphs stay the default). x = the main joint's angle of each picture (unsmoothed, from the CSV), y = the force shown in the Force strip (smoothed with the chosen moving average, newtons when calibrated, else volts). A thin line goes through every picture, with a dot per picture coloured from purple (the start of the trial) to yellow (its end), larger dots inside the analysis window (the blue band follows when it is dragged), a star at the peak force (with the angle read at the peak, the same number as the Force tab), and a ring that follows the video. The force is paired with the picture that shows the same moment: a picture is stamped *Picture delay* seconds after it was taken, so the force at `t - delay` goes with the picture stamped `t` (the same rule as the angle at peak force). Pictures without an angle (lost dots) or outside the recorded force are left out, never filled in. Code: `analysis.force_angle_path`, `analysis.time_colours`, `ReviewTab._update_force_angle`.
- **Changes no number.** It only draws numbers that are already shown (tested: the Angles, Force and Check texts are the same with the view on).
- **Not tested:** on a real trial with a person (the synthetic trial has a made-up force); a long trial with 60 pictures per second.
- Tests: new `test_force_angle.py` (12). Version 0.17.0. **Full suite on the final code of 0.14.0-0.17.0: 829 passed, 1 skipped, 0 failed** (17.4 min, nothing else running). Looked at in a real window: a synthetic trial with simulated force (the path, the window, the star and the ring).

## 0.16.0 - 2026-10-20

### Reference readings: what a goniometer or an inclinometer said, typed in beside the app's own angle
- **Why:** the angles have never been compared with a hand instrument, and a number typed from one can be kept with each trial, compared with the app, and used to validate it. A typed value is a number a person wrote down, **never a measurement of this program**; an empty box means "not measured" and a typed 0 is a reading of 0 degrees.
- **Live tab, a new section *Reference reading (goniometer, inclinometer)*:** choose the instrument (goniometer, digital inclinometer, other) and what it is read to; press **Reading taken now (G)** at the moment you read the instrument, which keeps the app's own angles of that moment (the unsmoothed angle averaged over the 0.2 s before, so it does not depend on the display smoothing); type what the instrument said in the box of each angle (several readings of one angle separated by a space, a comma is the decimal mark; up to 5, they are averaged and all kept). A frontal test also has boxes for the typed hip flexion and knee (the protocol key `reference_extras`: these are not angles of the picture). A box that cannot be read is marked and keeps its old value. The section's header says what is held ("2 typed, moment kept").
- **Like for like:** the goniometer can only be read at rest, so the app's angle is the one kept at *Reading taken now*, not the hold of the contraction (the knee moved about 5.8 deg between rest and hold in the first force trials). If no moment was kept, the first second of the recording stands in and every table says so.
- **Safety against a silent wrong number:** the readings belong to a position (test and target). They stay for the second trial of the same position, but **are never saved with a trial of another position**: `meta.json` then says `reference_readings.not_used` with both positions, and the Live section says in amber that they will not be saved. Typing a new reading at a new position replaces the old ones. Nothing can be changed while recording. Saved in `meta.json` `reference_readings` (every reading, the mean, instrument, resolution, the moment, the app's angles at it, the position, a note) and `reference_extras`.
- **Review, a new tab *Reference*** (between Force and Calibration): the readings beside the app's angle at the same moment and the difference (app minus reference), with the instrument and where each came from. **Add or change the reference readings...** saves to a small file next to the trial, `<trial>_reference.json`, never into the trial's own files (tested byte for byte); a reading saved with the trial can be changed or removed there (an explicit "removed" entry). **Reference validation...** (top bar) goes through every trial in the recordings folder: per angle the number of pairs, the average difference, the spread, the 95 % limits, the largest difference, an agreement plot (difference against the mean of the two, with the average and the limits) and **Save the table as CSV** (`reference_validation.csv`, one row per reading). Two trials of one position share one reading and one stamp and count **once**. The report quotes the proposed acceptance of `SETUP_AND_VALIDATION.md` 4A (average within 0.5 deg, limits within +-1 deg) and says that a handheld goniometer cannot demonstrate +-1 deg because it is read to about a degree and has an error of its own of a few degrees; use a jig with a digital inclinometer for that claim. `session_summary.csv` gets five columns for the main joint (`reference_main_deg`, `reference_instrument`, `app_main_at_reading_deg`, `app_minus_reference_main_deg`, `reference_app_basis`).
- **Changes no measured number:** the angles, the tracker, the CSV columns and the recording are untouched; the typed values never enter an angle. The Review tabs have a new order (6 tabs).
- **Not tested:** with a real goniometer or inclinometer on a person; whether the 0.2 s average at the moment of the reading is a fair comparison for a limb that is not completely still; the G key while a text box has focus (a letter typed in a box is not a shortcut, as for the other keys).
- Tests: new `test_reference.py` (45: parsing, the saved form, the side file, the comparison, the agreement, folders, the engine), `test_reference_review.py` (11), `test_reference_live.py` (10); `test_analysis.py` updated for the new tab; `protocol.py` accepts `reference_extras`. Version 0.16.0.

## 0.15.0 - 2026-10-20

### Hip abduction and adduction with the camera in front, and a hip centre that is computed live
- **Why:** the protocol has four frontal positions (hip abduction and adduction at 0 and 20 deg, Tabel 2), so the plan showed 15 positions instead of 19. The frontal camera is there to control how far the participant is abducted or adducted, which the study counts among its most important measures; the sagittal posture (hip flexion 0, straight knee) is controlled by having the participant stand against a wall (heel, buttocks, back touching) and is not measured. The hip joint centre cannot be palpated (the joint is deep), so it is computed, live, instead of being calculated from the data afterwards.
- **Two new tests, `hip_abduction` and `hip_adduction`** (`"view": "frontal"`, positions 0 and 20 deg): the plan now has 19 positions + belt squat. Three dots: the ASIS of the tested leg, the ASIS of the other side, the centre of the patella. The same camera is moved to the front; no second camera. No strap or anchor dots in these tests.
- **Two angles per test, both live and in the CSV.** *Goniometer angle* (`abd_goniometer` / `add_goniometer`): Tabel 3 as written, fulcrum the tested ASIS, one arm towards the other ASIS, the other arm to the patella centre; the unsigned interior angle minus 90 for abduction, 90 minus it for adduction (so the sign is the test's own direction, and it does not depend on which leg or on mirroring). It is the main joint: judged against 0 / 20 deg, green/red. *About the hip centre* (`abd_hip_centre` / `add_hip_centre`): the same thigh line drawn from the computed hip joint centre, the point that really rotates; shown, saved, **never judged** (new optional angle key `judged`, default true).
- **The hip centre is a computed point** (new `derived_points` in `protocol.json`, kind `hip_centre_frontal`; an arm of an angle may end at one). Harrington et al., J Biomech 2007;40:595, equation set 1, right hip, mm, origin the midpoint of the two ASIS: sideways (towards the tested side) 0.33 x PW + 7.3, down 0.30 x PW + 10.9, PW = the distance between the two ASIS = picture pixels / the ruler scale. Computed in every picture (a few multiplications, far below the 10 ms the tracking takes), drawn as a cyan diamond, saved as `hip_centre_x`, `hip_centre_y` in `data.csv`, defined in `meta.json` `derived_points`. **The ruler is needed** (the equation is in mm): without it the hip-centre angle is blank, the header says so, and Lock is refused (it refuses while any angle is unavailable).
- **What is and is not known about the equation:** the constants were typed from a secondary source (a biomechanics wiki, through a search summary) and the coordinate origin from a validation paper that uses the same system (PMC5121588); **the original table was not read: check it before the numbers are reported.** Independent consistency check: a cadaver study (Seidel et al. 1995) puts the hip centre 14 % of the pelvic width medial to each ASIS, 90 mm at PW 250 mm; the equation gives 89.8 mm (tested in `test_hip_centre.py`). Reported mean errors of the equation in the validation paper: about 5.9 mm sideways and 5.5 mm down; soft tissue over the ASIS adds to that.
- **The two angles do not share a zero.** Synthetic pelvis 250 mm wide, thigh 400 mm from the hip centre: the goniometer reads -4.1, 0.0, 4.1 and 12.4 deg where the thigh is 0, 5, 10 and 20 deg out about the hip centre; so the goniometer's 0 is about 5 deg and its 20 about 29 deg about the hip centre. Which one belongs in the AnyBody model, and where AnyBody puts zero hip abduction, is to be agreed with AnyBody Technology. Both are in every file, so nothing has to be recalculated.
- **Operator:** a frontal test replaces *Participant faces* by **Tested leg**, adds an optional **ASIS to ASIS, tape** box and an *Against a wall: heel, buttocks, back touching* tick (saved as `sagittal_posture`). With the participant facing the camera the right leg is on the left of the picture (reversed for a mirrored image): **dots in the wrong order are caught before Lock** (a swapped ASIS pair would turn abduction into adduction without another sign), also a patella above the ASIS or a thigh shorter than the distance between the ASIS. The tape measure is a cross-check of the ruler: the program warns when the picture's ASIS distance and the tape differ by more than 8 % (ruler not at the pelvis' distance, pelvis turned, or a misplaced dot); it changes no angle. The Participant-faces check is not run in these tests. The tested leg is remembered; the tape value and the wall tick are not.
- **Review** reads the computed point from the CSV and draws it; trials recorded before 0.15.0 open as before. `AngleDef` has two new optional fields, `needs` (the dots clicked for an angle whose arm uses a computed point) and `judged`.
- **Changes no measured number of the sagittal tests:** the tracker, the angle maths and every existing column are untouched; `tests/golden_tracking.npz` is unchanged. `synthetic.render` skips limb lines for dots a picture does not have (the pictures of the existing tests are the same).
- **Not tested:** on a person (no frontal picture of a person exists yet: the ASIS dot may be hard to see or slide on the skin, the patella centre is a soft-tissue point), against a goniometer or inclinometer, in a real session; pelvis rotation about the vertical axis shortens the ASIS distance and shifts the hip centre; no torque from the front (the moment arm needs the hip centre and the line of pull; to be decided with AnyBody). The layout was looked at in a real window on a synthetic trial.
- Tests: new `test_hip_centre.py` (19), `test_frontal_engine.py` (21), 14 new cases and 2 new tests in `test_protocol_validation.py`, 4 in `test_protocol_table2.py`; `test_pipeline.py` and `test_strap_dots.py` updated for the two new tests; the label-length rule in `test_steps.py` caught my first checkbox text (57 characters, the panel's limit is 48). Version 0.15.0. **Full suite on the final code: 751 passed, 1 skipped, 0 failed** (23.9 min; a first full run had two failures, both mine and fixed: the old list of tests in `test_pipeline.py` and the checkbox text length). Looked at in a real window: a synthetic frontal trial recorded and opened in Review (cyan diamond, both read-outs, yellow position line).

## 0.13.0 - 2026-10-19

### Review of the first real session (P11, 15 Oct, 11 trials) and what was changed because of it
- **Why:** the P11 session was the first with a person, the tape dots, the load cell and the automatic markers together. Every trial's `meta.json`, CSV and video was read again, and the live loop was replayed on this laptop (same processor as in the trials).
- **The live picture ran at 4 to 11 pictures per second in every trial with the automatic MVIC markers (camera: 30). Fixed.** `pipeline_timing` in the 11 trials: the 9 with the automatic markers ran at 4.5 to 11.3 pictures/s with 77 to 200 ms of the program's own work per picture; the two without at 20 and 28. Cause, measured: `ForceSource.samples_between` looked through **every** stored force chunk on every call (10 ms chunks, 10 minutes kept = 60,000 chunks, **13 ms per call** once the force had been connected for 10 minutes), and a recording, the automatic markers and the force trace each call it several times a second, all competing with the picture thread. It now walks back from the newest chunk and stops at the first one that ended before the window (the chunks are always in time order): the same samples (tested against the old full scan on 300+ windows), 0.01 ms per call. Replayed through the whole window (a P11 video served as a live stream, a simulated force with 10 minutes of history, automatic markers on, recording): **old code 17-19 pictures/s, new code 29.5 (the camera's own rate)**; the engine's own work per picture went from 49-55 ms to 12-14 ms. The real session was slower than the replay (4-11), so other costs of the real chain (DroidCam, the NI driver) are not excluded: **check `pipeline_timing.loop_fps` in the next trial's `meta.json`.** The saved videos were tagged with the camera's 22-30 fps although only 4-11 pictures per second were saved, so they **play 2-4 times too fast in a normal video player** (Review uses the CSV times and is not affected); with the loop at the camera's rate this goes away. **No measured number changes** (the same force samples go to the same places).
- **The recording stops by itself 2 s after the MVIC end marker** (automatic or the E key). P11's recordings ran on for 1.5 to 39 s after the end marker before Stop was pressed (one of 47 s for an MVIC that ended at 8 s; one went on while the participant walked away, with every dot lost). Markers section: *Stop the recording by itself after the MVIC end* (on) and *Stop this long after the end* (2 s, 0.5 to 30). The record box counts down ("Stopping by itself in 1.4 s"); the window then stops it exactly as the Stop button does and says "Press R for the next trial". `meta.json` gets `stopped_automatically: {after_mvic_end_s}` (not `stopped_because`, which Review shows as a problem). Remembered in `settings.json`. May be changed during a recording (it decides only when the recording ends). Code: `Engine.auto_stop_s`, `Engine.seconds_to_auto_stop()`, `AUTO_STOP_AFTER_END_S` in `automvic.py`.
- **Record asks when the force has not been zeroed.** 4 of the 11 P11 trials (12:00 and the three hip flexion 0 deg trials at 14:47, after the program was restarted) have volts but **no newtons and no peak force**, because Zero had not been pressed since the start. Record now asks "The force has not been zeroed since the program started ... Record anyway, without newtons?"; No opens the Force step. The volts of those 4 trials are complete, so newtons can still be worked out afterwards with a zero taken from the same rig (see HANDOFF).
- **'Participant faces' is now also checked from the bend of the knee** when the four foot dots are not all marked. The two hip-extension-with-knee-90 trials (13:38, 13:41, lying face down) were recorded with *faces right*; the knee read **-55 and -78 deg** (impossible over-straightening; the knee was really bent about 55-78 deg) and the hip sign was flipped too, and nothing warned because the foot dots were switched off (the only facing check used them). A knee bends one way only: when it is bent more than 25 deg (`KNEE_FACING_MIN_DEG`) the "wrong" way, the view is the mirror one. The existing warning and lock block are used, with the text "the knee bends the wrong way ... lying face down usually needs the other side than sitting or lying on the back". Run over all 23 real recordings in `recordings/`: it flags exactly those two trials (41 of 55 and 28 of 37 pictures) and nothing else. **A third P11 trial had the wrong setting and is not caught:** 12:00, hip extension knee 0, standing facing left with *faces right* (knee read -12 and hip -11 deg, really about +12 and +11): its knee was nearly straight, which tells nothing. With knee-0 tests, switch the foot dots on or check the setting by eye. New `geometry.knee_bend_handedness`, `foot_handedness`; `view_handedness` uses the foot first, then the knee.
- **The 'click dot: ...' prompt is yellow on a darkened band**, and every text line on the picture has a darkened band behind it (white text on the pale wall was hard to read; screenshot of the P11 picture). Only how the picture looks changes, also in `overlay.mp4`.

## 0.12.0 - 2026-10-15

### The step list follows a session: participant first, privacy, ruler, force and markers are steps, one dot can be redone, the markers can be tried without recording
- **Why:** feedback after using 0.11.0 ("works way better"): a dot that was clicked on the wrong thing could only be fixed by marking every dot again; the dot colour was hidden under *Position*; privacy, the ruler, the force and the markers were not part of the step list at all, so nothing reminded you of them; the participant has to be known before the position (the session plan counts that participant's saved trials); and the automatic MVIC and the beeps could only be tried by recording a trial.
- **The strip now has ten chips, in the order of a session:** Participant, Camera, Privacy, Position, Dots, Ruler, Lock, Force, Markers, Record. A tick is done, the amber filled one is the next thing to do, an amber outline is still to do, grey is not possible yet. **Privacy, Ruler, Force and Markers are asked every session**: they stay amber until they are done, or until you tick the "not today" box in their section (*I looked: nothing identifies the participant*, *No ruler today*, *No force today*, *I mark the MVIC by hand today*). Those ticks are deliberately **not remembered**: the question comes back every session, because the picture, the ruler and the rig change.

## 0.8.0 - 2026-10-13

### Automatic MVIC start and end markers from the force
- **New tick box in the Record box: *Mark the MVIC automatically from the force*** (needs the force connected), with *Start when force rises by* (default 10 N) and *MVIC length* (default 7 s, the protocol's 1-5-1 tempo: ramp 1 s, hold 5 s, relax 1 s). **Pressing Record arms it.** When the force clearly leaves its rest level (the ramp begins) the program writes the **MVIC start** marker, and the **MVIC end** marker 7 s after it. They are the same markers the S / E keys write (same labels, CSV `event` column, `meta.json` events), so Review's window, the Check tab and the exports read them unchanged. Pressing S or E by hand takes the markers over. The picture header (and so the saved overlay video) and the Record box say *armed, waiting for the ramp* / *3.2 / 7 s* / *start and end marked*; the marker banner says *(automatic)*.
- **How the ramp is found** (`limbtrack/automvic.py`): the force (newtons without the zero, only the rise matters; volts with a 0.02 V threshold if there is no load cell slope) is averaged over 20 ms (one 50 Hz cycle: the hum cancels exactly). The rest level is the median of that signal from 3.0 s to 0.5 s before now, so a slow drift is followed and the ramp itself is never part of the reference; the force from just before Record is used, so a ramp that begins at once is found. The start is called when the force is at least the threshold away from the rest level, has moved at least 40 % of the threshold within the last 0.25 s (a slow pre-tension is not a ramp) and both hold for 70 ms (a knock is not a ramp). The threshold is raised to 6 x the noise of the rest level if the rest was unsteady. Either direction of force counts. The end marker is placed on the first picture 7.0 s after the start marker.
- **Measured on made-up force traces** (`tests/test_automvic.py`): for the protocol's ramp (400 N in 1 s) the start marker goes in **0.11 s after the force begins to rise** (100 N in 1 s: 0.18 s; 200 N in 3 s: 0.25 s; 1000 N in 0.5 s: 0.11 s), and the program's estimate of when the force really began is within 0.03 s. Ignored: 50 Hz hum of 47 N (90 mV), a pre-tension of 8 N per second, knocks of up to 50 ms, a rest that sways 6 N. A push of 15 N on a swaying rest is not called, a 60 ms knock is. In real-time recordings with the simulated force (3 runs, pictures rendered at about 20 per second) the start marker went onto the picture **0.14 to 0.21 s after the real start of the ramp** (read from the saved `force.csv`) and the end marker 2.53 to 2.62 s after the start for a set 2.5 s (the end goes on the first picture after it is due, so with 30 pictures per second it is at most 0.03 s late); the estimate of the ramp's start was within 0.001 s there (`tests/test_automvic_engine.py`).
- `meta.json` gets `auto_mvic_setup` (on or off, threshold, length; frozen while recording like every setting) and, when on, `auto_mvic`: what happened (state, the times of the markers, the force's estimated onset and how long after it the start marker came, the rest level and noise, the threshold used). Review's Check tab says the markers were automatic, or, if the force never rose by the threshold, that no start was marked (use *Window = force above half of peak*).
- **What can change a measured number: nothing.** Force volts and newtons, dot positions, angles and the CSV values are exactly as before; only the `event` column and the marker list can contain markers the operator did not press. The start marker is about 0.15 to 0.2 s later than the true start of the ramp (it is not moved back: the rows are already written); the true start estimate is saved. Markers sit on the picture time stamps like those pressed by hand, so the *picture delay* applies to them as to everything else. **Not tried:** the real load cell and DAQ (only the simulated source); check the first real session's marker against the force in Review.
- One MVIC per recording: after the end marker nothing more is marked automatically.
- **Test fix (no program change): three tests in `tests/test_analysis.py` (the two torque tests and the picture-delay test) failed on an idle computer, and on the committed 0.7.2 code too.** Their helper `humming_trial` replaces the force of a real 3 s recording with a known 17 s signal but kept the real picture times, which end at about 7.5 s on an idle machine (the recording is 90 pictures with a 33 ms wait each plus the time to render them); the tests look at 8 to 13 s. - **New calibrations need no code change**: `LoadCellCalibration/logs_to_points.py FOLDER` turns the LogFile CSVs of a session into a points file (and flags short, unsteady or wrongly named runs), `LoadCellCalibration/add_calibration.py POINTS.csv --id NAME --activate` fits it and stores it. Older recordings keep the id of the regression they were measured with.
- **Zero** (button or **Z**) is the only step before a session and can be repeated as often as the set-up changes: it takes 1 s of signal as 0 N and says how far it moved. **The zero is not kept when the program closes**: a new start shows and saves volts only until the first zero, so a wrong zero can never carry over. The zero used is saved in every trial's `meta.json`.
- **Volts are still the permanent record**: every sample is saved as measured (`force.csv`, `force_v`); newtons are the second channel.
- **Review**: new *Calibration* tab with the regression (points up and down, the line, how far each run is from it with the +-95 % band, this trial's peak and plateau marked) and in words how precise this trial's peak and plateau are (+- N and %), with a warning for forces beyond the heaviest calibration load. The *Force* box has a **Zero** box and *Recalculate newtons*: it applies the zero in the box and the active regression to the saved volts (to correct a wrong zero, or to use a newer calibration). The export has `force_regression_id` and `force_peak_95pct_n`.
- *Re-calibrate with a known weight* is kept but only for the present session (not saved).
- Removed: `force_calibration.json` (it kept the zero between sessions).

## 0.5.0 - 2026-10-09

### Force (load cell through an NI DAQ, new)
- New **Force** box in the Live tab: source (NI DAQ, or a simulated contraction to try the program), device, input, wiring (differential or single-ended), *Connect*, a live read-out in N (or V until calibrated), *Zero* and *Calibrate with a known weight*. The force and its peak are drawn in the picture header and the saved overlay video.

- New dependency `nidaqmx` (and the NI-DAQmx driver, already installed on this computer).

From the first tests with a board and black markers (recordings of 2026-10-09).

### Tracking (tracking numbers can differ slightly: at most 0.27 px on the Bundepus reference video)
- A dot that touches a shadow, a finger or a strap is no longer dragged toward it: when no blob fits or the blob is too big or too long, the search is repeated at higher contrast thresholds, which cut the attachment away. This also finds a lost dot again while a finger still touches it.
- The learned dot size no longer follows a merged blob (it had grown to twice the dot size).
- Small fragments of a dot hidden by a hand are no longer accepted as the dot (lower area limit 0.3 to 0.40 x the dot area; a half-covered dot, about 0.5, is still tracked and flagged).
- On the board recordings the dots stay on the dots through finger contact (checked on pictures); the tracked dot of the first trials is no longer lost for 131 and 44 frames when replayed.

### Ruler
- The two ruler dots are fixed points, not tracked (nothing can lose them). The scale is constant; a camera or ruler moved after marking is not noticed, so mark it again.
- Review draws the ruler of the trial and shows `ruler N cm = X px/cm` (or `no ruler scale`) in the title line.

### Speed
- Measured on this computer (real window, real camera, recording with overlay): 30 fps live and 29.6 fps while recording, so the computer is not what limited the first board recordings (17-26 fps); the camera or phone delivering fewer frames (dim light) fits the frame spacing better.
- Blobs are measured all at once instead of one by one (same numbers to 1e-13 px; about 2.7 x less time per dot in a cluttered scene), and the extra high-threshold search for a dot merged with a shadow is skipped when nothing could be that bright or dark. Worst case (8 dots all lost in a busy picture): 27 ms per frame.
- Every recording's `meta.json` has `pipeline_timing`: the program's work per frame (mean, 95th percentile, max), the time between frames (median, 95th percentile, max), the loop frame rate and the share of the interval spent working. If work is much smaller than the interval, the camera or phone is the limit.

### Recording
- The raw and the overlay video are encoded by two threads in parallel (insurance for slower computers; on the development computer encoding was not the cause of the 17-26 fps seen in the board recordings: the writer queue never held more than 2 frames).

## 0.3.0 - 2026-10 (pilot build)

Changes after the first audit and the simplification decisions. Details and reasons are in `FEATURES.md`.

### Measurement and tracking
- Lost-dot rule: frozen position, fixed search circle, strict resume checks (round, right size, bright enough).
- A covered dot can no longer take a fast-moving neighbour (neighbours are protected where they will be; duplicate trackers are resolved by fit to prediction).
- The Auto dot colour is decided on every click and kept only if the marking succeeds.
- Partly covered or cut-off dots are flagged (warning only).
- Re-marking prefers lost dots and never lands on a neighbour; clicks on the video are ignored while recording.
- Display smoothing is a 0.2 s moving average and never touches the saved numbers; the reference stored at Lock does not depend on it.

### Protocol
- `protocol.json` follows Tabel 2 of the 2026-09-28 draft (hip extension with knee 0 and knee 90, positions and required neighbour angles); validated at start-up.
- The knee is signed (hyperextension negative); a test without positions shows the main joint without judging it.
- A wrong "Participant faces" setting is detected from the marked dots and Lock is refused.
- Three-point angle as interior angle or as flexion, without the mirror-image target trap.

### Scale, strap and displacement
- Pixel scale from a ruler with a dot at each end; dot size in cm against the 2 cm minimum.
- Optional strap and anchor dots; angle of pull, moment arm and strap-to-joint distance.
- Review: dot displacement, pull table, hold-plateau angle, rest-to-hold shift, identifying columns in the exported summary.

### Recording
- CSV written row by row, complete `meta.json` from the start, safe closing, settings frozen while recording and snapshotted at the start.
- Video encoded on its own thread; the overlay video is optional (Review can export it later).
- A silent live camera is waited for and reopened; gaps, failed reads and reconnects are recorded; a picture-size change stops and saves the recording.
- Videos carry the source's own frame rate; CSV `frame` is the video frame index; new last columns `source_frame` and `<dot>_partial`.
- Exposure-lock button switched off; webcams open on automatic exposure.

### Input
- Webcam opened in the right order (MJPG last), granted format and measured frame rate shown and saved; mirror switch; error log for the video thread.
